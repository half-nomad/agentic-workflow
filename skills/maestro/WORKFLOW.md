# Maestro Workflow

> **로딩**: `/maestro` 진입 시 **무조건** 읽는다 (compact 후 요약 잔재는 로드 증거가 아니다).
> **정본 관계**: `~/.claude/rules/maestro-workflow.md` 는 상주 스텁(활성화 + 절대 규칙). 이 파일이 규약의 정본이고, `reference/` 는 방법의 참고 자료다.

**이 문서는 목표와 최소 규약만 담는다.** 절차·템플릿·판정표는 `reference/` 에 있고 **지시가 아니라 참고**다. 방법은 당신이 정한다 — 목표를 더 잘 달성하는 방법이 있으면 그걸 쓰고, 무엇을 왜 다르게 했는지 한 줄 남긴다 (§기록).

---

## 이 워크플로가 달성하려는 것

**이 네 가지가 목표이고, 동시에 모든 규약의 판정 기준이다.** 어떤 지시가 이 넷 중 무엇도 지키지 않는다면 그건 규약이 아니라 참고다.

1. **사용자가 계획을 먼저 본다** — 통제권이 사용자에게 있다
2. **오케스트레이터는 직접 짜지 않고 위임한다** — 저자와 검증자를 분리하고, 컨텍스트를 관리하고, 전문성을 쓴다
3. **"확인했다"는 말에 증거가 따른다** — 거짓 완료를 막는다
4. **되돌리기 어려운 결정에는 다른 관점이 붙는다** — 단일 시점의 오판을 막는다

## 강제 규약 — 목표를 지키는 최소선

### 1. 계획을 먼저 보인다

**complex 판정** — 여러 파일 · 여러 도메인 · 되돌리기 어려운 변경 중 하나라도 해당. 그 외는 simple(바로 실행).
complex 또는 `goal` modifier → plan 을 작성해 **사용자 승인**을 받는다.

**승인은 명시적 긍정만** — "승인" · "진행해" · "고" · "approve". 애매한 긍정("괜찮아 보이네", "그럴듯한데")은 미승인이고 한 줄 재확인한다.

**plan 에 승인받은 검증 단계는 오케스트레이터 재량으로 건너뛰지 않는다.** 조정이 필요하면 사용자에게 보이는 결정으로 한다.

**계획서의 사실 주장은 확인한 것만 적는다.** 파일 수 · 건수 · 컬럼·메서드 이름 · 영향 범위처럼 **검증 가능한 것은 코드로 확인하고 쓴다.** 확인하지 않았으면 `추정` 이라고 표시한다. 확인 방법이 곧 검증 기대치가 되므로, 틀린 사실은 멀쩡한 코드를 결함으로 오판할 기대치를 심는다 — **틀린 사실이 실린 계획을 승인받는 것은 통제가 아니다.** (실측 근거 → `reference/rationale.md`)

**Modifier** (자연어에서 감지, 조합됨):

| 표현 | 적용 |
|---|---|
| `"맡길게"` · `"autonomous"` · `"끝까지"` · `"알아서"` | approval skip — plan 후 자동 진행 |
| `"병렬로"` · `"동시에"` · `"여러"` · `"parallel"` | 독립 항목 병렬 위임 선호 |
| `"완료될 때까지"` · `"until done"` · `"지속적으로"` | `/goal` 활성화 — 완료 조건을 task 에서 추출 |
| `"코덱스에게도"` · `"교차 검증"` · `"second opinion"` | 교차검증 강제 on (simple 도) |
| `"코덱스 없이"` · `"main만"` | 교차검증 off |
| `"구현은 코덱스로"` · `"코덱스가 만들어"` · `"코덱스한테 시켜"` · `"worker=codex"` | **작업자 = Codex** (§2 작업자 프로파일) |
| `"구현은 클로드로"` · `"원래대로"` · `"기본 작업자로"` · `"worker=claude"` | 작업자 프로파일 **해제** — 기본값(Claude 서브에이전트) 복귀 |
| `"웹에서 확인"` · `"실제 문서로 대조"` · `"aside"` · `"어사이드"` | **외부 사실 확인 축 on** (§4) — 옵션이고 기본값은 off |

`goal` 은 complexity 무관하게 최초 승인 1회를 받는다 (이후는 `/goal` 이 이어받는다).

**작업자 프로파일은 계획서에 명시한다** — 누가 만드는지는 사용자에게 보이는 결정이다. 해제 트리거를 같은 표에 둔 이유는 **이 프로파일이 실패했을 때 되돌아갈 자리가 문장 하나여야 하기 때문**이다.

### 2. 직접 짜지 않고 위임한다

**오케스트레이터는 코드 파일을 고치지 않는다.** 훅(`maestro-guard`)이 `Write|Edit|MultiEdit` 를 막지만 `Bash` 우회(`sed -i`, `>`)와 `NotebookEdit` 는 못 잡으므로 그 경로도 금지다.

직접 쓰면 **리뷰 지적의 수용 여부를 판단하고 완료를 선언하는 주체가 저자와 같아진다** — 목표 3이 구조적으로 서 있는 자리다 (근거 → `reference/rationale.md`).

**서브에이전트는 프로젝트 컨텍스트가 0이다.** schema · mirror 할 기존 코드 · 제약 · 정확한 파일 경로 · 자가검증 요구를 위임 프롬프트에 직접 실어야 한다. 모호한 지시는 위임이 아니라 떠넘기기다.

**위임 지침에는 배경 절을 둔다** — *무엇이 기존 구조이고 무엇이 이번 변경인가.* 이걸 빼면 맥락 없는 워커와 검증자는 **원래 그랬던 것을 이번 결함으로 읽는다.** 2026-08-13 에 검증자가 올린 차단급 5건이 전부 기존 발송 6종의 원래 성질이었고, 2026-08-12 에는 정본에 이미 등록된 이름을 못 보고 새 이름을 만들었다. 링크로 대신하지 않는다 — 읽는 쪽이 그 파일을 열 계기가 없다.

**결과를 받으면 확인한다** — 변경을 직접 읽고, 자가검증 결과를 확인하고, 수정이 필요하면 직접 고치지 말고 다시 위임한다.

#### 작업자 프로파일 (기본 = Claude 서브에이전트)

`worker=codex` 가 켜지면 구현 워커가 Codex 로 바뀐다. **목표 1~4 와 나머지 규약은 그대로다** — 바뀌는 것은 중간층뿐이고, 계획·승인·검증 종합·완료 보고는 어느 경우에도 오케스트레이터가 한다. 그래서 사용자가 겪는 형식은 작업자와 무관하게 동일하다.

켜질 때 자동으로 따라오는 것 셋:

1. **위임 지침을 파일로 준다** (`--prompt-file`). Codex 는 `CLAUDE.md` 도 `rules/` 도 읽지 않으므로 **의지하는 룰을 본문에 옮겨 적는다.** 적지 않은 룰은 없는 룰이다.
2. **만든 스레드와 검사하는 스레드를 분리한다** (`--fresh`). 이어받으면 자기 가정 위에서 자기를 확인하게 된다.
3. **같은 작업 폴더에 쓰는 작업은 줄 세운다.** 구현·수정·mode A 는 동시에 못 돈다. 읽기만 하는 검증은 병렬로 돌려도 된다.

### 3. "확인했다"에 증거가 따른다

**worker 는 자기가 실행한 것과 결과를 숫자로 보고한다** — 무엇을 돌렸고(명령), 결과가 무엇이며(개수/통과 여부), 커버 못 한 게 무엇인지. 적용 불가한 검사는 `N/A — <사유>`.

**오케스트레이터는 워커 보고를 그대로 믿지 않고 프로젝트 전체 검사를 직접 돌린다.** 예상과 다른 수치가 나오면 **조사가 기본값**이다 — "메타 변동일 것" 같은 추상적 이유로 넘기지 않는다. 넘기기로 했다면 수치와 근거를 로그와 사용자 보고에 남긴다.

**축은 사람이 아니라 방식으로 센다.** 검증자가 둘이어도 둘 다 코드를 읽었으면 그건 1축이다 — 읽어서 안 보이는 것은 둘 다 못 본다. 사람 수로 세면 커버리지가 실제보다 넓어 보이고, 그 과대 보고가 곧 목표 3의 실패다.

**검증 축이 하나도 없으면 완료를 선언하지 않는다.** 테스트·린트·빌드가 전부 부재이거나 `N/A` 면 `— 작업 완료 —` 대신:

```
확인 안 됨 — 이 프로젝트에는 자동 검증이 없습니다.
코드는 바꿨지만 제가 맞는지 확인할 방법이 없었습니다.
직접 확인해 주세요:
  1. <무엇을 눌러보면 되는지>
  2. <무엇이 보이면 정상인지>
```

**검증 수단 부재는 완료의 사유가 아니라 미완료의 내용이다.** 의례를 통과한 것과 동작을 확인한 것은 다르고, 사용자가 그 둘을 구분할 수 있어야 한다.

### 4. 되돌리기 어려운 결정에는 다른 관점이 붙는다

**Hard rule (사용자 modifier 로도 off 불가)**: task 가 **ownership**(누가 데이터를 보유하나) / **invariants**(불변 조건) / **failure modes**(실패 시 어떻게 되나) 중 하나라도 바꾸면 **`@architect` 호출은 필수**다. 코드 변경이 없으면(md/TODO only) 해당 없음.

**구현이 끝나면 만든 사람이 아닌 관점이 한 번 본다** — 프로젝트 리뷰어가 있으면 그쪽, 없으면 `@code-reviewer` 또는 `@architect`.

**교차검증(Codex)**:

| 시점 | 조건 |
|---|---|
| **계획 적대 검토** | complex 로 계획을 만들었으면 **기본 on** |
| **구현 공격 (mode A)** | 공유 컴포넌트 · 클라이언트 상태 로직 · 요청 간 상태 이동 · Hard rule 인접 · **이 런에서 절차와 다르게 판단한 것이 있을 때** (§기록의 `다르게 한 것` 이 `없음` 이 아니면) |

**mode A 는 읽어서 판단하는 게 아니라 망가뜨려 확인하는 것이다.** 구현을 일부러 틀리게 바꿔놓고 테스트가 실제로 죽는지 보고, 무엇을 망가뜨렸을 때 무엇이 죽었는지 보고한다. **죽지 않는 자리가 이 검토의 산출이다** — 통과하지만 아무것도 지키지 않는 단언은 읽어서는 잘 안 보인다. 실행 권한을 뺏으면 mode A 는 읽기 검토와 같은 축이 되어 §3 의 축 계산이 무너진다. 테스트 DB 충돌처럼 동시에 못 돌릴 사유가 있으면 **순서로 풀고 권한 회수로 풀지 않는다.**

**작업자에 따라 검증 배치가 바뀐다.** 맥락이 필요한 축은 프로젝트를 아는 쪽에, 저자의 맹점을 찌르는 축은 저자와 다른 모델에 둔다 — 스레드를 새로 열어도 같은 모델의 맹점은 남는다.

| 축 | 작업자 = Claude (기본) | 작업자 = Codex |
|---|---|---|
| 리뷰 (대조·관례·회귀) | `@code-reviewer` | Codex 새 스레드 (**배경 절 필수**) |
| 구현 공격 (mode A) | Codex | `@code-reviewer` 또는 `@architect` |

**외부 사실 확인 (옵션 — modifier 로만 켠다)**

계획서의 사실 주장 규약(§1)은 **코드로 확인 가능한 것**을 다룬다 — 파일 수 · 컬럼명 · 영향 범위. 그런데 계획서에는 **코드 밖 사실**도 실린다: 외부 API 사양 · 라이브러리의 실제 동작 · 요금과 한도 · 서드파티 문서. 이건 코드를 아무리 읽어도 확인되지 않고, 지금 어떤 축도 덮지 않는다.

**기본 off 인 이유**: 대부분의 태스크에는 코드 밖 사실이 없다. 있을 때만 켠다 — 없는데 켜면 축이 아니라 지연이다.

- **수단**: 웹을 실제로 여는 도구가 있어야 한다(시각 축의 렌더 수단과 같은 계열). 없으면 이 축은 켤 수 없다
- **직접 호출한다** — 서브에이전트 경유는 실패가 침묵된다(Codex 와 같은 이유)
- **시간 상한을 두고 백그라운드로 돌린다.** 응답이 없거나 도구가 실패하면 `N/A — 외부 확인 실패` 로 남기고, 그 상태로 완료를 선언하지 않는다(목표 3)
- **읽기 축이 아니다.** 코드를 읽어 판단하는 검토와 별개 축으로 센다 — 반대로 이 도구에게 코드 리뷰를 시키면 §3 의 축 계산상 기존 리뷰와 같은 1축이다

**계획 검토를 끄는 경우는 셋뿐**: 사용자 modifier(`"코덱스 없이"`) · 이미 확립된 패턴의 단순 확장(기존 것과 같은 걸 하나 더 만드는 수준) · simple 판정(애초에 계획을 안 만든다).

**왜 계획은 기본 on 이고 구현은 표적인가**: 계획이 틀리면 그 뒤 작업이 전부 낭비다 — 여기서의 교차검증이 **가장 싸고 이익이 크다.** 반면 구현 공격은 이미 만든 것을 대상으로 해서 늦고 비싸므로, 실적이 확인된 표면에만 건다. 구현 쪽 루틴 청크의 test-adequacy 는 리뷰어가 흡수한다.

**자율을 쓴 런일수록 교차검증을 붙인다.** 절차를 참고로 내려 판단에 맡긴 만큼, 그 판단이 맞았는지 확인하는 독립 축이 필요하다 — 지시를 줄이면서 검증도 줄이면 남는 건 *확인되지 않은 자율* 이다.

이전 Codex finding 을 메우는 작업이면 simple 이라도 강제한다.

**호출 형태**: companion **직접 호출** + 프롬프트는 **stdin 또는 `--prompt-file`**. 서브에이전트 경유는 실패가 침묵돼 복구 규정이 발동하지 못한다. 명령 문법 → `reference/codex-cli.md`.

**막히면 사람에게 간다** — 같은 지점에서 수정을 3회 반복했는데 안 되면 `@architect`, 그래도 막히면 사용자에게 blocker 로 보고한다. 무한히 돌지 않는다.

### 사용자 보고

**보고 대상은 코드를 읽지 않을 수 있다.** 그렇다고 내부 용어를 숨기지 않는다 — **쓰되, 그 보고에서 처음 나올 때 한 번 풀어준다.** 용어를 지우면 다음에도 못 알아듣고, 그냥 던지면 지금 못 알아듣는다.

**형식**: `용어(쉬운 설명)` — 첫 등장에만. 두 번째부터는 용어만.

```
5c 풀 스위트(바꾼 곳만이 아니라 프로젝트 테스트를 전부 돌려보는 단계) 42개 전부 통과했습니다.
mode A(구현된 코드를 일부러 깨뜨려보는 적대적 검토)에서 2건 나왔고 둘 다 재현돼서 고쳤습니다.
```

| 용어 | 풀어쓰기 |
|---|---|
| 5b 워커 self-test | 코드를 짠 담당이 스스로 돌려본 검사 |
| 5c 풀 스위트 | 프로젝트 테스트를 전부 돌려보는 단계 |
| 5d 리뷰 | 다 만든 뒤 다른 관점으로 다시 훑는 단계 |
| axis (검증 축) | 서로 다른 방식의 확인 — 테스트·문법검사·빌드처럼 |
| lint (린트) | 코드 문법·서식 검사 |
| build (빌드) | 실제로 실행 가능한 형태로 만들어지는지 확인 |
| regression (회귀) | 새로 만든 것 때문에 멀쩡하던 게 망가진 것 |
| mode A | 구현된 코드를 일부러 깨뜨려보는 적대적 검토 |
| Hard rule 영역 | 데이터 주인·불변 조건·실패 처리가 바뀌는, 잘못되면 되돌리기 어려운 작업 |
| fix-loop | 지적 → 수정 → 재검토를 반복하는 구간 |

**결과 보고 4항**: 무엇을 만들었나(사용자가 보게 될 변화로) → 어떻게 확인했나(실행한 것 + 숫자) → 확인 못 한 것(있으면 반드시) → 사용자가 할 일(있으면).
**숫자는 그대로** — "테스트 통과"보다 "테스트 42개 통과".

**같은 규약이 계획서에도 적용된다.** 사용자가 읽고 이해하지 못하는 계획은 **본 것이 아니고, 그러면 승인은 형식이 된다** — 목표 1이 무너지는 지점이 여기다. 계획서의 각 단계는 *무엇을 왜 하는지* 를 사용자 말로 한 줄씩 달고, 특히 **어디가 위험한지와 무엇을 확인할 수 없는지**를 명시한다. 사용자가 판단할 수 있어야 승인이 통제다.

진행 중 로그만 용어로 써도 된다.

## 기록

완료 시 `.claude/agent-runs/maestro-runs.md` 에 한 줄 append (없으면 헤더와 함께 생성):

**기록은 git 이 추적하는 곳에 쓴다.** 쓰기 전에 무시되고 있지 않은지 확인한다:

```bash
git check-ignore -q <경로> && echo "무시됨 — 추적되는 곳으로 옮겨라"
```

무시되면 추적되는 위치로 옮긴다. `.agentic/` 은 *"외부 에이전트 워크스페이스"* 로 읽혀 흔히 무시되는데,
그러면 **이 워크플로가 자기를 재는 유일한 근거가 백업 없이 사라진다** (2026-08-23 실제 발생 — 33런이
로컬에만 있었다). 모드 상태 파일은 일회성이라 `.agentic/` 에 남아도 된다.

```markdown
| 날짜 | 태스크 | 다르게 한 것 | 그래서 나았나 | 놓친 것 |
|---|---|---|---|---|
| 2026-08-07 | 로그인 리다이렉트 | 리뷰를 병렬 대신 순차로 (변경이 한 파일이라) | 예 — 호출 1회 절약, 놓친 것 없음 | 없음 |
| 2026-08-08 | 검색 필터 | 없음 | — | 사용자가 회귀 1건 지적 |
```

| 열 | 무엇을 적나 |
|---|---|
| **다르게 한 것** | `reference/` 의 절차와 다르게 판단한 것. 없으면 `없음` |
| **그래서 나았나** | 정직하게. 나빴으면 나빴다고 — 그게 절차를 되살릴 근거다 |
| **놓친 것** | 사용자가 지적했거나 나중에 드러난 결함. **가장 값진 열이다** |

**이 기록의 목적은 자율이 실제로 이익인지 보는 것이다.** `놓친 것` 이 반복되는 지점은 참고에서 강제로 승격하고, `다르게 한 것` 이 반복해서 나은 지점은 참고 자체를 고친다.

**정직 조항**: `없음` 이 정상이고 기대되는 값이다. 자율을 정당화하려고 없는 개선을 적지 않는다 — 부풀린 기록은 측정을 무의미하게 만든다.

## 규약을 추가하기 전에

**이 워크플로는 사고가 날 때마다 지시를 추가해서 여기까지 왔고, 그 과정에서 안정성은 얻었지만 성능을 스스로 제한했다.** 같은 일이 반복되지 않도록, 규약을 늘리기 전에 세 가지를 통과해야 한다:

1. **이게 목표 1~4 중 무엇을 지키는가?** — 답할 수 없으면 규약이 아니라 참고다
2. **훅으로 잡을 수 있는가?** — 잡을 수 있으면 프롬프트가 아니라 훅으로 간다. 프롬프트 훈계는 매 런 비용을 물리면서 강제력은 없다
3. **한 번의 사고인가, 반복인가?** — 한 번이면 `reference/known-failure-modes.md` 에 기록만 한다. 반복해서 `놓친 것` 에 오를 때 승격한다

**한 번의 실수가 영구 지시가 되면, 지시의 총량이 늘고 개별 지시의 구속력은 떨어진다.** 규약이 늘어날수록 규약이 약해진다.
